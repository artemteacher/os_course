## Тема: виртуальная память своими глазами — два коротких опыта

## Цель работы

Увидеть на практике, как ОС на самом деле выделяет память программе и как устройство памяти (страницы, TLB, кэш процессора) влияет на скорость программы.

## 1. Как устроена работа

Работа состоит из двух небольших опытов. Каждый опыт — это короткая программа (обычно 20–40 строк) и несколько вопросов, на которые нужно ответить по результатам в отчете (!!!).

**Язык программирования — любой.** В приложении А есть подсказки для C, C++, Rust, Go, Python, Java, C# и JavaScript (Node.js). Если вы пишете на другом языке, найдите в нём аналоги.

Если ваш язык ведёт себя не так, как описано в задании, — это не ошибка, а результат: запишите его и попробуйте объяснить.

**Прежде чем запускать** каждый опыт, запишите в отчёт короткий прогноз: что, по-вашему, получится. За неверный прогноз оценка не снижается — важно потом честно сравнить прогноз с результатом.

## 2. Подготовка

1. **Нужен Linux.** Подойдёт любой вариант:
   - Linux, установленный на компьютере;
   - Windows: WSL2. Работайте в домашней папке Linux (`cd ~`), а не в папках `/mnt/c/...`;

2. **Нужно около 2 ГБ свободной оперативной памяти** (посмотреть: `free -h`, столбец `available`). Для опыта 1 достаточно блока 256 МиБ (при наличии ресурсов можно использовать 1 ГиБ), а для опыта 2 при нехватке памяти возьмите N = 4096 вместо 8192.
3. **Компилируемые языки собирайте с оптимизацией**: `gcc -O2`, `cargo build --release` и т. п.

## 3. Общие инструменты

Всё нужное о памяти своего процесса программа может узнать, прочитав два текстовых файла. Это работает в любом языке, где можно прочитать файл.

**Виртуальная и резидентная память.** В файле `/proc/self/status` найдите строки `VmSize:` (общий размер виртуального адресного пространства процесса) и `VmRSS:` (приблизительный объём резидентной памяти). Числа указаны в килобайтах. Эти показатели относятся ко всему процессу, а не только к исследуемому блоку.

```
VmSize:    280000 kB
VmRSS:       9876 kB
```

**Сколько было страничных исключений (page faults).** Файл `/proc/self/stat` — одна строка с полями через пробел. Достать из неё нужное число можно так:

```
текст = прочитать файл "/proc/self/stat"
хвост = часть текста после ПОСЛЕДНЕЙ закрывающей скобки ")"
поля  = хвост, разбитый по пробелам
minor = поля[7]     (нумерация с нуля)
```

Число растёт с момента запуска процесса. Чтобы узнать, сколько прерываний произошло за какой-то этап, вычтите значение до этапа из значения после.

**Совет.** Напишите функцию, которая печатает VmSize, RSS (в МиБ) и число minor faults с подписью этапа, например `print_mem("после выделения")`, и вызывайте её в нужных местах.

**Время.** Измеряйте монотонными часами своего языка (см. приложение А): разница двух замеров — это прошедшее время в миллисекундах.

**Размер страницы.** Обычно 4096 байт (4 КБ). Узнать точно: команда `getconf PAGESIZE` или функция вашего языка (приложение А).

**Ловушка оптимизатора.** Компилятор или JIT может устранить обращения к памяти, если докажет, что они не влияют на наблюдаемый результат. Проверяйте фактически записанные значения и используйте предусмотренные языком способы сохранения реальных обращений (например, volatile-доступы там, где это уместно, или барьеры оптимизации). Простая печать одного байта либо заранее вычислимой суммы сама по себе не всегда достаточна.

## 4. Задания: нужно провести два опыта

### Опыт 1. «Выделить — не значит получить»

**Цель:** сравнить резервирование виртуального адресного пространства с предоставлением физических страниц при чтении и записи.

**Язык программирования — любой.** По возможности используйте **анонимное отображение памяти с чтением и записью** (аналог Linux `mmap` с `MAP_PRIVATE | MAP_ANONYMOUS`) без предварительного заполнения, `MAP_POPULATE` и принудительного предварительного доступа к страницам. Для этого разрешено использовать стандартную библиотеку, стороннюю библиотеку или вызов системного API из выбранного языка. Если получить такое отображение нельзя, используйте большой массив или другой механизм выделения памяти вашего языка и **обязательно укажите в отчёте**, чем он отличается от анонимного отображения. В этом случае некоторые результаты могут оказаться несопоставимыми; объясните ограничения своего варианта. Подсказки приведены в приложении А.

1. Определите размер страницы в Linux (`getconf PAGESIZE`). В начале программы измерьте `VmSize`, `VmRSS` и число minor page faults (раздел 3). **До первого запуска** запишите прогноз изменения этих показателей после выделения, чтения и записи.
2. Создайте блок размером **256 МиБ** (268 435 456 байт; при достаточном объёме памяти можно использовать 1 ГиБ). Пока **не читайте и не записывайте** его содержимое. Снимите показатели ещё раз.
3. **Первое чтение:** последовательно прочитайте по одному байту из каждой страницы. Накапливайте прочитанные значения в контрольной сумме, которую выведите на экран. Измерьте время только обхода, затем снимите показатели памяти.
   ```
   сумма = 0
   для i от 0 до размер_блока - 1 с шагом размер_страницы:
       сумма += блок[i]
   ```
4. **Первая запись:** запишите значение `1` в первый байт каждой страницы. Измерьте время обхода и повторно снимите показатели.
   ```
   для i от 0 до размер_блока - 1 с шагом размер_страницы:
       блок[i] = 1
   ```
5. **Повторная запись:** в те же позиции запишите значение `2`. Измерьте время и показатели ещё раз. Затем прочитайте несколько **именно записанных** позиций (например, `0`, `размер_страницы`, `2 * размер_страницы` и последнюю записанную позицию) и проверьте, что они содержат `2`. Убедитесь, что оптимизатор не устранил исследуемые обращения к памяти; при необходимости примените механизм защиты от оптимизации, подходящий для вашего языка.
6. Освободите блок (для отображения — снимите отображение), затем снова измерьте `VmSize` и `VmRSS`.

*Время замеряйте только для обходов, без чтения `/proc` и вывода на экран. Прирост minor faults для каждой строки — разница с предыдущим измерением. Показатели зависят от Linux, настроек ядра и среды выполнения; совпадение с прогнозом не обязательно.*

**Вопросы для отчёта.**

1. Как изменились `VmSize` и `VmRSS` после выделения блока? Чем виртуальная память отличается от резидентной? Если RSS вырос сразу, почему по одному этому факту нельзя утверждать, что язык явно записал нули во все страницы?
2. Сколько страниц базового размера помещается в вашем блоке? Сравните это число с приростом minor faults при чтении и записи. Почему значения могут не совпадать (например, из-за уже предоставленных страниц, zero page, Transparent Huge Pages и работы среды выполнения)?
3. Почему чтение ранее не использованной страницы может вызвать minor fault, но не привести к сопоставимому увеличению RSS? Всегда ли это наблюдалось у вас?
4. Почему первый проход с записью может сопровождаться ростом RSS? Какая работа требуется ОС при первом обращении на запись?
5. Сравните время первого и повторного проходов с записью. Объясните разницу **или её отсутствие**, не предполагая заранее, что повторный проход обязательно будет в разы быстрее.
6. Что изменилось после освобождения блока? Почему память процесса не обязательно вернулась точно к исходным показателям?
7. Каким способом вы выделили память? Если использовали обычный массив, управляемую кучу или отображение файла вместо анонимного отображения, как это могло повлиять на результаты?

**Важно.** `VmRSS` — приблизительный показатель для всего процесса. Minor fault не равен «выделена одна новая физическая страница»: исключение может разрешиться без чтения с диска и без предоставления отдельной страницы. Linux может использовать общую нулевую страницу и большие страницы. Не пытайтесь подгонять измерения под ожидаемый ответ.

## 5. Если что-то пошло не так

| Что вы видите | Возможная причина | Что сделать |
|---|---|---|
| Опыт 1: RSS вырос сразу после выделения | Среда выполнения коснулась страниц, аллокатор изменил кучу или измерения захватили постороннюю работу процесса | Укажите способ выделения; попробуйте анонимное отображение и сравните `VmSize` с RSS |
| Опыт 1: чтение вызвало minor faults, но RSS почти не вырос | ОС могла использовать общую нулевую страницу | Объясните различие между созданием отображения и выделением приватных физических страниц |
| Опыт 1: время прохода почти нулевое, ожидаемых обращений не видно | Оптимизатор мог исключить цикл или измеряется не тот участок | Проверьте реальные обращения и используйте языковые средства против их устранения |
| Опыт 1: minor faults намного меньше числа страниц | Возможны Transparent Huge Pages или предварительное предоставление страниц | Проверьте `cat /sys/kernel/mm/transparent_hugepage/enabled` и опишите способ выделения |
| Опыт 1: после освобождения RSS не вернулся к исходному | Runtime или аллокатор оставил память для повторного использования; RSS измеряется для всего процесса | Зафиксируйте результат и объясните ограничения измерения |
| Опыт 2: разница между обходами маленькая | Программа собрана без оптимизации или в Python используются обычные списки | Соберите с `-O2` / `--release`; в Python используйте numpy |
| Компьютер стал сильно тормозить, процесс завершился со словом `Killed` | Не хватило оперативной памяти | Уменьшите размер блока (опыт 1) или N (опыт 2) |

## Приложение А. Подсказки по языкам

Во всех языках `VmSize` и `VmRSS` можно читать из `/proc/self/status`, а minor faults — из `/proc/self/stat` (раздел 3). Для опыта 1 предпочтительно анонимное отображение; обычные массивы разрешены с объяснением особенностей среды выполнения.

### C / C++
- **Время:** `clock_gettime(CLOCK_MONOTONIC, &ts)`; в C++ — `std::chrono::steady_clock::now()`.
- **Размер страницы:** `sysconf(_SC_PAGESIZE)`.
- **Опыт 1:** `mmap(NULL, size, PROT_READ | PROT_WRITE, MAP_PRIVATE | MAP_ANONYMOUS, -1, 0)`; проверить `MAP_FAILED`, затем `munmap`. `malloc` и `new[]` допустимы как альтернативы, но их поведение зависит от аллокатора. Для измерения фактических обращений при оптимизации используйте подходящую технику (например, volatile-доступ через корректно полученный указатель).
- **Сборка:** `gcc -O2 -o prog prog.c`.

### Python
- **Время:** `time.perf_counter()` (в секундах).
- **Размер страницы:** `mmap.PAGESIZE`.
- **Опыт 1:** `mmap.mmap(-1, 256 << 20)` создаёт анонимное отображение с доступом на чтение и запись; освободить через `close()`. `bytearray` допустим как альтернативный вариант, но его инициализация и использование памяти могут отличаться.
- **Опыт 2:** numpy (`pip install numpy`): `a = np.arange(N*N, dtype=np.int32).reshape(N, N)`. По строкам — цикл по `i` с суммой `a[i, :].sum()`, по столбцам — цикл по `j` с суммой `a[:, j].sum()`. Сумму среза считает numpy, поэтому цикл на Python здесь всего N итераций.

### Go
- **Время:** `start := time.Now()`, затем `time.Since(start)`.
- **Размер страницы:** `os.Getpagesize()`.
- **Опыт 1:** анонимное отображение через `golang.org/x/sys/unix.Mmap` (или другую подходящую библиотеку) с `MAP_PRIVATE | MAP_ANON` и последующим `Munmap`. `make([]byte, size)` — допустимая, но не эквивалентная альтернатива из управляемой кучи Go.

### Rust
- **Время:** `let t = std::time::Instant::now();`, затем `t.elapsed()`.
- **Размер страницы:** `libc::sysconf(libc::_SC_PAGESIZE)` (пакет `libc`) или команда `getconf PAGESIZE`.
- **Опыт 1:** `libc::mmap` и `libc::munmap` (потребуется `unsafe` и проверка результата); `Vec<u8>` допустим как альтернативный вариант, но он не гарантирует аналогичного поведения выделения.
- **Защита от оптимизатора:** `std::hint::black_box(значение)`.
- **Сборка:** `cargo build --release`.

### Java
- **Время:** `System.nanoTime()` (в наносекундах).
- **Опыт 1:** в стандартном Java API нет прямого аналога анонимного `mmap`. Можно использовать соответствующую нативную библиотеку (FFM/JNI/JNA) либо обычный `byte[]` с объяснением влияния JVM. Альтернативный способ — `FileChannel.map(FileChannel.MapMode.PRIVATE, ...)` для временного файла, но это **файловое**, а не анонимное отображение: результаты первого чтения могут отличаться. Не считайте рост RSS сразу после `new byte[]` обязательным.
- **Опыт 2:** `int[] a = new int[N * N]`, запуск с `java -Xmx1g ...`.

### C#
- **Время:** `var sw = System.Diagnostics.Stopwatch.StartNew();`, затем `sw.Elapsed.TotalMilliseconds`.
- **Опыт 1:** можно вызвать системный `mmap` через P/Invoke (с корректной проверкой результата и `munmap`); альтернативно использовать `NativeMemory.Alloc` (неуправляемое выделение, не строго эквивалентное `mmap`) или обычный массив с описанием различий. Для небезопасного кода включите `<AllowUnsafeBlocks>true</AllowUnsafeBlocks>`.

### JavaScript (Node.js)
- **Время:** `performance.now()` (в миллисекундах).
- **Опыт 1:** в стандартном Node.js нет прямого анонимного `mmap`; можно использовать подходящий нативный модуль или `Buffer.alloc`/`Uint8Array` как альтернативу с обязательным объяснением поведения V8 и инициализации памяти. Не предполагайте, что создание массива обязательно коснётся всех физических страниц.
- **Опыт 2:** `new Int32Array(N * N)`.
